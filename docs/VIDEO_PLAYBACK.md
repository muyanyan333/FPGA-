# TF 卡视频播放

## 使用方法

1. 当前 TF 卡 MVI4 全屏 30 帧媒体配套下载 `lab_ex5_i2s-work/src/td_project/video_quality30.bit`。用户已确认可用的 `video_framefix.bit` 保留作旧 MVI3 媒体回退。此版本关闭摄像头，使用 MVI4 逐帧调色板、30 帧目标、音频采样同步及片尾自动恢复图片轮播。旧 `video_no_camera.bit` 保留作 8 帧回退版本。
2. TF 卡使用工程已有的 exFAT 文件系统，保留原有 MUSIC、picture 目录。
3. 本次视频已放入 `E:\VIDEO`：

   | 文件 | 用途 |
   |---|---|
   | `01.MVI` | FPGA 读取的 MVI4 逐帧调色板索引视频帧 |
   | `00.wav` | 与视频配套的 48kHz、16位、立体声音轨 |
   | `戒不掉_原始视频.mp4` | 下载原片，供电脑查看；FPGA 不直接解码 |
   | `video_info.json` | 转换规格记录 |

4. 使用新版网页或 Android 2.1.0，在“视频 / 摄像头”页面点击“播放 TF 卡视频”。点击“返回图片与音乐”退出。
5. 该页面提供音量滑块、加减音量及静音。共 0～10 档，与音乐共用；画面模式切换保留音量和静音状态。音量状态以 FPGA 的 `0x87` 回传为准。

配套音轨播放结束、PCM FIFO 排空且 I2S 尾部输出完成后，自动返回图片模式并恢复轮播，不自动循环。再次进入视频模式可以从头播放。首次进入需初始化 TF 卡并扫描目录，请等待状态回传。本版本不启用摄像头。

启动顺序为：扫描配套文件 → 写入并提交第一帧 → 预填充音轨 → 开始音画播放。视频首帧就绪前停止 SDRAM 显示读取，避免读取未初始化的帧缓存。视频尚未显示时，HDMI 黄底表示等待文件发现，青底表示文件已找到、等待首帧提交，红底表示缺少文件或读取错误。

排查青屏使用 `camera_player_video_stage_debug.bit`。青底上的黑条数量表示当前阶段：1 条等待 SDRAM 写请求应答，2 条等待应答释放或缩放器就绪，3 条读取视频数据，4 条读取 FAT 簇链，5 条等待缩放完成，6 条等待 SDRAM 完整帧写入完成。它是诊断版，不代表青屏根因已经修复。`video_startup_tb.v` 的 `REAL_WRITER=1` 已接入工程实际异步写 FIFO 和帧写控制器，验证首帧完整提交及随后音轨预填充。

### 不含摄像头的对照版本

`video_no_camera.bit` 使用 `top_video_player`，摄像头采集、SCCB 初始化、摄像头写 FIFO 均在综合时移除；RESET_N=0、PWDN=1，摄像头接口保持复位和待机。图片、音乐、视频、音量控制及首帧黑条诊断保留，摄像头切换命令被顶层拒绝。APK 不需要更新，但其中摄像头按钮无法进入摄像头模式。

当前构建命令为 `build_video_framefix.tcl`，时序约束为 `timing_video_no_camera.sdc`。此版本用于排除摄像头逻辑和资源占用的影响，不能据此认定原黑屏由摄像头导致；原 8 帧无摄像头版本已由用户确认可播放；20 帧版本需单独上板验证。

## 转换其他视频

```powershell
python tools/prepare_video.py 输入.mp4 输出目录 --ffmpeg 你的ffmpeg.exe
```

工具流式转换，最多取前 300 秒。输出目录已有 `01.MVI` 或 `00.wav` 时会停止，避免覆盖。先在电脑转换完成，再将配套的两个文件放入 TF 卡同一层子目录；当前播放器选择扫描到的第一组视频和 `00.wav`，因此卡内只保留一组视频文件。

默认 MVI3：仍为 320×240、20 帧，每像素使用一字节索引。文件前 1,024 字节依次为 `MVI3`、256 项 RGB888 调色板（768 字节）及填充；后续每帧 76,800 字节索引。调色板由整个原片生成并固定，FPGA 使用同步 BRAM 查色。兼容 MVI1/MVI2，不支持旧固件直接读取 MVI3。

这次修正使用真实 WAV EOF 的独立视频锁存及尾部 I2S 排空时间；结束条件不再依赖最后一帧读控制器退回空闲。音轨由工具按视频帧数精确补齐，因此音轨播放完即复位媒体流水线并返回图片。等待重新扫描到图片后发送一次自动轮播命令，之后仍可手动切换模式。

历史 MVI2：320×240、RGB332、20 帧/秒，每帧 76,800 字节。文件头四字节 `MVI2` 占用首帧底部左侧四个像素并显示黑色。R/G 为 3 位、B 为 2 位，硬件扩展到 RGB888 后缩放显示。颜色层次少于 RGB565；它降低 TF 读取流量，使 20 帧的总净数据量约为 1.728 MB/s（含音轨）。目标帧率不等于已测量的实机帧率。

每帧使用 2,400 个实际从 PCM FIFO 消费的立体声采样作为截止时间。若到期帧尚未提交，暂停取下一个音频采样，I2S 时钟持续运行并输出静音；帧提交后恢复，避免读卡延迟持续累积为音画偏移。静音/音量不改变采样计时。显示切换仍有 HDMI 刷新量化和音频流水线延迟，需要上板检查口型及长时间同步。

加 `--profile rgb565_8` 可生成原 8 帧文件，新固件根据 MVI1/MVI2/MVI3 签名自动选择格式与时基；旧固件无法识别 MVI2。

MVI1 不含 MP4 等压缩编码。当前约定为连续的、由下向上排列的 320×240 RGB565LE 帧，每帧 153,600 字节；文件头四字节 `MVI1` 占用第一帧底部左侧两个像素，这两个像素显示为黑色。无声原片也生成等时长静音 WAV，用来提供统一的 48kHz 播放时基。WAV 为固定 44 字节标准 PCM 头，末尾补静音或裁切，与视频总帧数匹配。

文件目录扫描沿用 48 项候选文件和 8 个一级子目录上限，不递归扫描更深子目录。视频与音频数据支持连续簇和 FAT 链寻址；播放器不支持直接解码 MP4/H.264，也不支持快进、进度拖动或多视频列表。

## 串口协议

四字节控制帧不变：`A5 CMD ARG CHECK`，`CHECK=A5^CMD^ARG`。

| 命令 | 参数 | 功能 |
|---|---|---|
| `1D` | `00` | 图片 / 音乐 |
| `1D` | `01` | 摄像头 |
| `1D` | `02` | TF 卡视频 |
| `20` | `00`～`0A` | 设置音量，解除静音 |
| `21` / `22` | `00` | 音量加 / 减一级，解除静音 |
| `23` | `00` / `01` | 解除 / 开启静音 |

`0x86` 状态帧：`5A 86 MODE VIDEO_FLAGS 00 00 00 CHECK`。MODE 为 0/1/2；VIDEO_FLAGS 的 bit0 表示找到配套文件，bit1 表示视频读取器处于活动状态，bit2 表示读取器错误、扫描后缺少文件或音轨解析错误。模式、标志和校验和使用同一份发送快照。进入视频模式不等于已经成功读出第一帧，以上位机状态提示及 HDMI 实际输出为准。

上位机新增“播放视频、打开视频、视频模式、播放戒不掉”和“停止视频、关闭视频、退出视频”等文字/手机语音别名。ASRPRO 的离线识别模型没有增加这些新词条，原有音量词条沿用相同串口命令。

### 逐帧配色与 30 帧目标

用户已确认 `video_framefix.bit` 可正常播放，作为稳定回退保留。新入口 `build_video_quality30.tcl`，独立输出 `video_quality30.bit`；保留 100MHz SDRAM 和现有图片、音乐、按键、语音、蓝牙功能。仅视频模式读块启动连续字节路径，50MHz 控制时钟下的字节间隔由 21 周期变为 18 周期，SCLK 峰值仍为 25MHz。物理 SPI 回归核对 CMD17 地址、512 个非恒定数据字节、两 CRC 字节和末尾停止；非视频、低速及未连接使能保持原时序。CRC 字节完整消耗，未新增 CRC 校验。

新 MVI4 每帧为 77,824 字节：`MVI4` + 256 项 RGB888 调色板 + 252 字节填充/参数 + 76,800 个索引像素；偏移 772 存放帧率（20/24/25/30）。仅第一帧读取帧率，分别对应每帧 2,400/2,000/1,920/1,600 个 48kHz 采样；其他帧不能改变音轨时间基准。调色板每帧更新，复用原有 palette RAM，无新增完整帧缓存；MVI1、MVI2、MVI3 继续识别。文件转换采用 Lanczos 缩放与 Bayer 有序抖动。`--fit cover` 保持人物比例、裁去超出屏幕比例的边缘并铺满画面；`--fit contain` 保留全画面并补黑边。
